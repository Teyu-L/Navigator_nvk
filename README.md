# UniNav — навигация внутри университетского корпуса

Мобильное одностраничное приложение (SPA), которое строит кратчайший маршрут
внутри корпуса **по трём этажам**, показывает его поверх реальных планов этажей
и объясняет, где нужно перейти на другой этаж.

Проект собран на **Vite + Vanilla TypeScript** без UI-фреймворка: интерфейс —
обычный DOM, маршрут рисуется на `<canvas>` поверх `<img>` с планом этажа.
Интерфейс полностью русифицирован, поиск понимает русские и английские
названия, номера аудиторий и сокращения.

---

## Что умеет приложение

- Ищет кратчайший путь по объединённому графу всех трёх этажей.
- Строит маршруты **внутри одного этажа** и **между этажами** (1 → 2 → 3).
- Соединяет этажи по лестницам, используя реальные имена лестничных узлов
  каждого этажа.
- Рисует маршрут только для активного этажа и показывает маркеры:
  - **A** — старт;
  - **B** — финиш;
  - **🛗** — точка перехода на другой этаж с подписью «Поднимитесь / Спуститесь».
- Разбивает многоэтажный маршрут на шаги по этажам; шаг можно нажать и
  переключиться на нужный этаж.
- Позволяет вручную переключать этажи 1 / 2 / 3 кнопками на карте.
- Поддерживает поиск по коду аудитории, номеру, русскому и английскому
  названию: `D105`, `105`, `Ауд. 105`, `Аудитория D105`, `Library`,
  `Санузел`, `Кафе`, `Столовая`, `Scool21` и т. п.
- Показывает понятные сообщения, если маршрут не найден или начало и финиш
  совпадают.
- Поддерживает deep links вида `?from=...&to=...`.
- Работает на телефоне (свайп, pinch-to-zoom) и на десктопе
  (колесо мыши, перетаскивание, кнопки масштаба).



## Интерфейс

```
┌─ Шапка ─────────────────────────────────────┐
│ 🎓 UniNav                                   │
│ [A] Откуда (Столовая, D105)…   ⇅  [B] Куда… │
├─ Карта ─────────────────────────────────────┤

```

### Deep links для проверки

Параметры `from` и `to` принимают id узла, код аудитории или название.
Сначала выполняется точное совпадение по id, затем — поиск по алиасам.

```
http://localhost:5173/?from=Кафе&to=K304
http://localhost:5173/?from=Санузел&to=Столовая
http://localhost:5173/?from=Scool21&to=F318
http://localhost:5173/?from=D102&to=D302
```

копирует в корень `dist/`.

## Данные

### Формат графа

Файлы `map/final_graph_floorN.json` содержат только геометрию:

```json
{
  "nodes": {
    "D105": { "x": 170, "y": 521, "floor": 1 },
    "D106": { "x": 170, "y": 534, "floor": 1 }
  },
  "edges": [
    { "from": "D105", "to": "D106" }
  ]
}
```

- `x`, `y` — координаты в пикселях исходного плана (750×750).
- `floor` — номер этажа.
- Рёбра неориентированные, вес вычисляется как евклидово расстояние между
  узлами в пикселях.
- Поисковые алиасы **не хранятся в JSON** — они генерируются в рантайме
  (`src/labels.ts`) из id узла. Это исключает расхождение между подписью и
  поиском и убирает дублирование данных.

### Планы этажей

Каждый план — самодостаточный SVG 750×750 с `viewBox="0 0 750 750"`.
Внутри нет внешних картинок, шрифтов и скриптов: только векторные пути
(на третьем этаже — ещё маски и `use`-ссылки на локальные `id`).

Графы размечены в координатах исходных растровых планов **750×750**, поэтому
JSON не переписывается: рендерер нормализует координаты на лету
(`src/renderer.ts`).

- Базовая система задана константами `BASE_WIDTH = 750`, `BASE_HEIGHT = 750`.
- Перед каждой отрисовкой у `<img>` с SVG берётся `getBoundingClientRect()`
  и считаются `scaleX = width / BASE_WIDTH`, `scaleY = height / BASE_HEIGHT`.
- Узлы и рёбра рисуются в точку `x * scaleX`, `y * scaleY`, поэтому линия
  всегда лежит на коридорах, как бы план ни был растянут.
- `<canvas>` — отдельный слой в screen-space поверх трансформируемого
  `stage`: `position: absolute`, `pointer-events: none`, `z-index: 2`.
  Его CSS-размер в точности равен видимому прямоугольнику SVG, а backing
  store — `round(size × devicePixelRatio)`, чтобы линия оставалась чёткой
  на Retina.
- На `resize`, `orientationchange`, `ResizeObserver`, а также на каждый
  zoom/pan canvas пересчитывается и перерисовывается через
  `requestAnimationFrame`. Промежуточные положения жеста не копятся: за кадр
  выполняется одна отрисовка.

SVG вставляется через `<img>`, поэтому вектор остаётся чётким при
масштабировании, а zoom/pan применяется CSS-трансформацией только к `stage`
(план + его позиция), тогда как слой маршрута живёт в координатах экрана.

## Как строится маршрут

1. **Загрузка этажей** (`GraphService.loadFloors`).
   Все три графа объединяются в один набор узлов и список смежности.
   Id узлов получают префикс этажа: `f1:D105`, `f2:D105`, `f3:stairs_D_south`.
   Это обязательно, потому что лестницы, санузлы и служебные узлы называются
   одинаково на разных этажах.

2. **Горизонтальные рёбра.**
   Внутри этажа вес ребра — евклидово расстояние между координатами.
   Дополнительно сохраняется исходный `rawId` (например, `D113_stairs_D_east`),
   который используется для подписей и поиска.

3. **Вертикальные связи.**
   Лестницы соседних этажей связываются по каноническим ключам, извлечённым из
   составных id:
   `stairs_D_south`, `D113_stairs_D_east`, `stairs_D_south_K108` → `D_south`.
   Переход между этажами стоит фиксированные `10000` условных пикселей.
   Это больше диагонали плана (~1060 px), поэтому маршрут между двумя точками
   одного этажа всегда остаётся на этом этаже, а не «срезает» через соседний.
   Для межэтажных маршрутов число переходов задано разницей этажей, поэтому
   штраф не мешает выбрать оптимальную лестницу. Поддерживаются реальные
   варианты имён: `stairs_F`, `stairs_F_north_F207`,
   `stairs_E_west_stairs_F` и т. п.

4. **Дейкстра.**
   `findShortestPath(startId, endId)` работает по объединённому графу.
   Если пути нет, возвращается `null`; если start = end — маршрут из одной точки.

5. **Разбиение по этажам.**
   Путь делится на `RouteSegment`; каждый сегмент знает свой этаж, список узлов,
   последний узел и `transitionToFloor` для перехода дальше.

6. **Отрисовка.**
   На активном этаже рисуется только его сегмент: две линии (тёмная обводка и
   яркая внутренняя), стрелки направления, маркеры A/B и маркер лестницы.
   Координаты каждого узла умножаются на текущий `scaleX`/`scaleY`, а толщина
   линий, стрелки и подписи масштабируются вместе с планом, поэтому маршрут
   выглядит одинаково на телефоне и на большом мониторе.
   На этажах без сегмента план остаётся доступным, но линия не рисуется.

## Поиск и подписи

`src/labels.ts` — единый источник:

- **`getDisplayName`** — человекочитаемое название:
  - `D103_D110` → `D103, D110 · Этаж 1`;
  - `K202_K203_K204` → `K202, K203, K204 · Этаж 2`;
  - `stairs_K_west_WC_K` → `Лестница K (зап.) / Санузел K · Этаж 3`;
  - `WC_F_F303` → `Санузел F (ауд. F303) · Этаж 3`;
  - `G103_Auditorium_hall` → `Актовый зал (ауд. G103) · Этаж 1`.
- **`buildAliases`** — варианты поиска:
  - код и номер аудитории: `D105`, `105`;
  - русские и английские слова: `Ауд.`, `Аудитория`, `Кабинет`, `Room`,
    `Auditorium`, `Class`;
  - достопримечательности: `Кафе`, `Cafeteria`, `Столовая`, `Библиотека`,
    `Медпункт`, `Деканат`, `Коворкинг`, `Школа 21`, `Актовый зал` и др.;
  - общие слова для лестниц, санузлов и входов: `Лестница`, `Stairs`,
    `Санузел`, `Туалет`, `Restroom`, `Вход`, `Entrance`.
- Служебные узлы коридоров (`*_Node1`, `I_Node1` и т. п.) исключены из поиска
  и из выпадающего списка.
- При равном совпадении результаты сортируются по длине названия и алфавиту,
  поэтому на запрос `Restroom` первым идёт именно `Санузел D · Этаж 1`, а не
  комбинированный узел «лестница + санузел».

## Состояние данных первого этажа

В текущей версии `map/final_graph_floor1.json` содержит **93 узла и 93 ребра**.
Проверка связности показывает, что все узлы первого этажа связаны, кроме
`Coworks_K110`: у него нет ни одного ребра. Поэтому маршрут *до* этой точки
построить нельзя (поиск её находит, но алгоритм возвращает «маршрут не найден»).

Важно: по условию задачи папка `map/` сейчас **не изменялась**. Чтобы включить
эту точку в маршрутизацию, достаточно добавить одно ребро к ближайшему узлу,
например `K111 ↔ Coworks_K110` (расстояние около 12 px), и пересобрать проект.

Ранее в этом же файле была другая проблема: он содержал данные второго этажа
(те же узлы и рёбра, `floor: 2`). Тогда граф был восстановлен из
`nodes_floor1.json` и сохранённых рёбер. Сейчас используется актуальная
93-узловая версия из `map/`, но с указанным выше изолированным узлом.

многоэтажные шаги. Никаких сгенерированных или «заглушечных» этажей больше нет.

## Рефакторинг и чистота проекта

В рамках финальной итерации:

- **удалены дубликаты данных**: `public/data/*` (старые копии графов) и
  `public/maps/*` (PNG-планы) — теперь единственный источник это `map/`;
- **удалён генератор-заглушка** `scripts/generate_data.js`, который создавал
  псевдо-этажи 2 и 3 из первого этажа;
- **исправлен выбор этажа в Дейкстре**: межэтажный переход стоит `10000`
  условных пикселей, поэтому маршрут `Кафе → D109` больше не идёт
  `1 → 2 → 1`, а остаётся на первом этаже;
- **рантайм использует только 3 SVG-плана и 3 итоговых графа** из `map/`;
  авторские скрипты и промежуточные JSON, которые могут лежать рядом, в
  сборку не попадают;
- **удалено неиспользуемое окружение** `venv/` (26 МБ), которое больше не
  требуется приложению;
- **убраны мёртвые поля и код**: `totalDistance`, `distance`,
  `transitionStairName`, `allNodes`, `RouteSegment.startNode`,
  `MapRenderer.getActiveFloor`, поле `fitScale`;
- **убраны неиспользуемые CSS-переменные** `--violet`, `--radius`,
  `--header-height` и стили чипов/метрик;
- **добавлен `src/data.ts`** как единственная точка подключения карт и графов;
- **добавлен `src/labels.ts`** как единственный источник подписей и алиасов;
- **исправлена сетка десктопа** после удаления блока чипов;
- **исправлено поведение поиска**: при редактировании поля старый выбранный
  узел сбрасывается, поэтому нельзя случайно построить маршрут от предыдущей
  точки; при фокусе на непустом поле показываются подсказки по введённому
  тексту.

Проверка перед сдачей: `npm run build` проходит без ошибок; в `dist/` лежат
только `index.html`, `robots.txt` и хешированные `assets/` (SVG-планы, JS, CSS),
без каталога `data/`; все импорты ведут только в `src/` и `map/`.

## Ручное тестирование (QA)

Проверено в браузере на dev-сервере (Vite, `127.0.0.1:5173`) и на
production-сборке (`vite preview`, `127.0.0.1:4173`). Визуальная проверка
дополнена чтением пикселей canvas и состояния DOM.

- **Сборка**: `tsc && vite build` — без ошибок; в `dist/assets/` три
  SVG-плана (`1floor-*.svg`, `2floor-*.svg`, `3floor-*.svg`), PNG-копий нет.
  В `dist/` нет каталога `data/`: старые копии графов удалены, в корень
  копируется только `robots.txt`.
- **SVG-планы**: каждый файл — самодостаточный SVG 750×750; внешних картинок,
  шрифтов, скриптов и ссылок нет, все `href="#…"` на третьем этаже указывают
  на существующие `id`. В браузере `naturalWidth/naturalHeight = 750`, а
  canvas подгоняется под **видимый** размер SVG: CSS-размер совпадает с
  `getBoundingClientRect()` картинки, backing store — `round(size × DPR)`.
  Координаты графа при этом не меняются (750×750) и умножаются на
  `scaleX`/`scaleY` при отрисовке.
- **Валидация графов**: нет рёбер в несуществующие узлы, петель и дублей;
  `floor` совпадает с номером этажа. Этажи 2 и 3 связны полностью; на этаже 1
  изолирован только `Coworks_K110` (см. раздел о состоянии данных).
- **Маршруты внутри этажа**: `D105 → D106`, `D105 → D109`, `J101 → I101`,
  `Санузел → Столовая`, `Кафе → D109` — ровно `1 этаж`. Проверено, что
  маршрут не уходит на другие этажи ради «среза»; на canvas есть линия,
  зелёный маркер A и красный маркер B.
- **Маршруты между этажами**:
  - `K101 → K201` — 2 этажа, шаги «Этаж 1 → Этаж 2», «Этаж 2 · финиш»;
  - `D102 → D302`, `K101 → K304`, `E101 → E301`, `J101 → J301`,
    `Scool21 → F318`, `деканат → K304` — 3 этажа.
  На каждом шаге подставляется свой SVG, рисуется только его сегмент, на
  промежуточных этажах видны фиолетовые маркеры лестниц с подписью
  «Поднимитесь / Спуститесь», на финишном — красный B.
- **Переключение этажей**: кнопки 1/2/3 и клик по шагу маршрута подсвечивают
  нужный этаж и сегмент. Если на выбранном этаже сегмента нет (например,
  `K101 → K201` и этаж 3), план показывается без линии и маркеров.
- **Поиск**: `D110` → `D103, D110 · Этаж 1`; `Restroom`/`WC` → `Санузел D ·
  Этаж 1` первым; `Санузел`, `Столовая`, `Кафе`, `Школа 21`, `Scool21`,
  `деканат`, `аудитория 105`, `305`, `K304` находят ожидаемые точки.
  Пустой запрос при фокусе показывает первые 10 точек, несуществующий —
  «Ничего не найдено».
- **Deep links**: `?from=Санузел&to=Столовая`, `?from=Scool21&to=F318`,
  `?from=деканат&to=K304`, `?from=аудитория 105&to=Компьютерный класс`
  (в том числе URL-encoded кириллица) сразу строят маршрут.
- **Сообщения**: совпадение точек → «Начало и назначение совпадают!»;
  недостижимый `Coworks_K110` → «Маршрут между выбранными точками не найден.»
  (маркеры A/B остаются); несуществующая точка не оставляет старый маршрут.
- **Сброс**: очищает поля, скрывает статус и шаги, убирает линию и маркеры
  с canvas (0 закрашенных пикселей).
- **Масштаб и панорама**: кнопки `+`/`−` меняют масштаб, `🎯` возвращает
  исходный; колесо мыши и перетаскивание работают; на touch-событиях
  проверены pinch-to-zoom и панорамирование одним пальцем.
- **Динамический масштаб координат**: после `🎯`, кнопок `+`, колеса,
  двойного клика и перетаскивания прямоугольник canvas совпадает с
  прямоугольником SVG (расхождение ≤ 0.01 px), а линия остаётся на
  коридорах. Проверено при масштабах 0.41 (fit), 0.60, 0.69 и 0.96:
  CSS-размер canvas равен размеру SVG, backing store — размеру × DPR
  (например, 646.4 px → 808 px при DPR 1.25).
- **Адаптивность**: проверены desktop 800×670, портрет 390×660 и
  ландшафт 660×390 / 568×320. В портрете элементы идут сверху вниз, в
  ландшафте управление уезжает в правую колонку, а карта занимает всю
  высоту экрана (400×390 и 308×320 px). После изменения размера контейнера
  `fit` и canvas пересчитываются автоматически (масштаб 0.4885 → 0.3787),
  горизонтальной прокрутки нет.
- **Production-сборка**: `vite preview` отдаёт хешированные `assets/*.svg`
  с `naturalWidth = 750`, deep link `?from=D102&to=D302` строит 3 этажа,
  переключение шагов подставляет `2floor-*.svg` и `3floor-*.svg`.
  В консоли нет ошибок, сетевых ответов 4xx/5xx нет.
- **Lighthouse** (production): Accessibility 100, Best Practices 100, SEO 100.
- **Убранные элементы**: чипов `0`, элементов `.summary-metric`/`.metric-value`
  `0`, текста с метрами и минутами в DOM нет.

## Деплой

Подробная пошаговая инструкция — в [`DEPLOY.md`](./DEPLOY.md). Кратко:

```bash
npm ci
npm run build
# содержимое dist/ выкладывается в корень сайта
```

Приложение — статический SPA без бэкенда: на сервере достаточно nginx,
Apache или любого static hosting. Все карты и графы уже встроены в
`dist/assets/`, отдельно копировать `map/` на сервер не нужно. Для nginx
нужен fallback `try_files $uri $uri/ /index.html;` и корректный MIME-тип
`image/svg+xml` (в стандартной конфигурации nginx он уже есть).

## Ограничения

- Графы заданы в пиксельных координатах плана, а не в метрах. Это осознанно:
  на экране не показываются расстояние и время, а маршрут всегда привязан к
  геометрии плана.
- Вертикальные переходы — только лестницы, размеченные в графах. Лифты
  поддерживаются тем же механизмом, если добавить их как узлы с ключом
  `stairs_*` (или расширить `extractStairKeys`).
- Названия и алиасы выводятся из id узлов; для новых аудиторий достаточно
  добавить узел в JSON — подпись и поиск появятся автоматически.
- Проект не использует бэкенд: все данные поставляются вместе со сборкой.

## Итог

UniNav — компактный, но полноценный MVP внутренней навигации: три реальных
этажа, векторные SVG-планы, единый граф, кросс-этажные маршруты по лестницам,
русскоязычный поиск, аккуратная отрисовка на canvas и минималистичный мобильный
интерфейс без лишних метрик. Данные, подписи и UI развязаны по модулям, а
`map/` содержит исходники карт и графов, из которых в сборку попадает только
необходимое.
